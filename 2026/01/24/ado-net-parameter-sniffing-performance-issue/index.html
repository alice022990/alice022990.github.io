踩坑記錄：ADO.NET 查詢慢但 SSMS 很快

Posted on 2026-01-24 Edited on 2026-02-01 In SQL Server , 後端開發 , 踩坑記錄

在做顯示特定大量資料的時候遇到顯示非常慢的問題，後來發現是 Ado.net 查詢很慢的關係，同樣的 sql script SSMS 執行不到 1 秒，但 Ado.net 卻需要近 1 分鐘，查了一些資料，一個一個試，最後發現是遇到參數嗅探。
試過

  1. WITH (NOLOCK)
    • 有變快一點點，但還是沒有達到理想中的速度
  2. 明確指定 SQL 型別
    • 資料庫的欄位型別跟 Ado.net 預設參數型別本來就一致(都是 NVARCHAR)，用了也沒有明顯差異
  3. 加上OPTION (RECOMPILE)
    • 本來需要快一分鐘，變成 10 秒內完成

參數嗅探 (Parameter Sniffing)

運作原理

當 SQL Server 第一次執行參數化查詢或預存程序時，會根據第一次傳入的參數值來產生執行計畫，並將該計畫存入快取 (Cache)。後續執行同個查詢時，會重複使用這個快取的執行計畫，以節省編譯成本。

潛在問題

當後續執行使用不同的參數值時，可能因為資料分布不均(Data Skew)，原本針對第一次參數優化的執行計畫不再適用，導致效能問題

範例

  • 第一次執行：@Status = 'Pending'(只有 100 筆資料)
    • SQL Server 產生使用 Index Seek 的計畫（適合小資料量），這個計畫被存入快取
  • 第二次執行：@Status = 'Completed'(有 100 萬筆資料)
    • 重用原計畫，但 Index Seek 對大量資料效率差，Table Scan 會更好

解決方案

1. OPTION (RECOMPILE) - 每次重新編譯

每次執行時都忽略快取的執行計畫，重新編譯執行計畫，根據當前參數值產生最佳計畫，執行完後，這個計畫不會被存入快取。

優點:

  • 保證每次都用「最適合當下參數」的計畫，解決特定參數慢的問題。
  • 適合參數值變化大且執行頻率不高的查詢

缺點:

  • 每次都需編譯成本，CPU 消耗較高
  • 無法利用計畫快取的優勢
  • 不適合高頻率執行的查詢
2. OPTION (OPTIMIZE FOR) - 指定優化參數值

如果知道某個特定的參數值最具有代表性（或是希望針對最頻繁出現的狀況優化），可以明確指定要針對哪個參數值進行優化，讓 SQL Server 為特定值產生執行計畫。

優點:

  • 可針對最常用或最重要的參數值優化
  • 保留計畫快取優勢
  • 效能可預測

缺點:

  • 需要事先知道最佳優化值
  • 對其他參數值可能不是最佳計畫
  • 資料分布改變時需要調整
3. 使用區域變數（Local Variables） - 避免參數嗅探

將參數值複製到區域變數，SQL Server 無法對區域變數進行參數嗅探，會使用統計資訊的平均值。

優點:

  • 避免極端參數值導致的差異計畫
  • 執行計畫相對穩定

缺點:

  • 失去參數嗅探的優勢，可能錯過更好的計畫
  • 當最佳計畫確實依賴參數值時效能會下降
4. OPTION (OPTIMIZE FOR UNKNOWN) - 使用統計平均值

強制 SQL Server 忽略實際參數值，使用欄位統計資訊的平均值來產生執行計畫。

優點:

  • 產生「通用」執行計畫，避免極端值影響
  • 計畫會被快取（省 CPU），效能較為穩定和可預測

缺點:

  • 可能對任何特定參數值都不是最佳
  • 當某些參數值明顯需要不同策略時會損失效能
  • 依賴統計資訊準確性
5. 計畫指引(Plan Guides) - 強制特定執行計畫

在不修改原始程式碼的情況下，為特定查詢指定執行計畫提示或強制使用特定計畫。

優點:

  • 不需修改預存程序或應用程式代碼
  • 可針對特定查詢精細控制
  • 適合第三方應用或無法修改的代碼

缺點:

  • 管理複雜度較高
  • 需要額外維護計畫指引
  • 除錯困難，不易發現問題來源
  • SQL Server 版本升級可能導致計畫指引失效
選擇建議
  • 執行頻率低且參數差異大 → 使用 OPTION (RECOMPILE)
  • 有明確主要使用場景 → 使用 OPTION (OPTIMIZE FOR)
  • 執行頻率高、需要穩定的效能表現 → 使用 OPTION (OPTIMIZE FOR UNKNOWN)
  • 無法修改代碼 → 使用計畫指引
  • 想快速測試 → 使用區域變數，但這通常不是長期方案
