JWT (JSON Web Token) 入門筆記

Posted on 2025-12-06 Edited on 2026-01-25 In 後端開發 , 身份驗證

JWT 介紹

JWT 是什麼？

JWT (JSON Web Token) 是一種基於 JSON 的開放標準（RFC 7519），用於在各方之間將訊息作為 JSON 物件安全地傳輸。常用於身份驗證和信息交換。

JWT 的結構

JWT 由三個部分組成，用點（.）分隔：

實際看起來像這樣：
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiaWF0IjoxNTE2MjM5MDIyfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

1. Header（標頭）

標頭通常包含兩部分：

  • typ: Token 的類型，通常是 JWT。
  • alg: 所使用的簽名演算法，例如 HMAC SHA256 或 RSA。

2. Payload

Payload 是 JWT 的實質內容，用於存放想傳輸的宣告 (Claims)。宣告是關於實體（通常是使用者）和其他資料的陳述，因為 Payload 傳遞的訊息最後是透過 Base64 進行編碼，是可以逆向解碼的，所以不可以放機密資訊。
常見的宣告類型有三種：

  • 註冊宣告 (Registered Claims)： 是 JWT 標準（RFC 7519）中預定義的聲明，建議使用，但非強制性。例如：
    • iss (Issuer)：發行者，標識是誰創建了這個 Token
    • iat (Issued At Time)：發行時間
    • exp (Expiration Time)：過期時間
    • sub (Subject)：JWT 的使用者（通常放用戶 ID）
    • aud (Audience)：接收此 JWT 的收件人
  • 公有宣告 (Public Claims)： 使用者可自定義，但為了避免衝突，建議在 IANA JWT Registry 中定義，或使用防衝突的命名方式（如使用 URI）。
  • 私有宣告 (Private Claims)： 為了在特定應用程式中共享資訊而創建的自定義宣告。

3. Signature（簽名）

簽名用於驗證發送者是誰，並確保 Token 在傳輸過程中沒有被篡改。
簽名是這樣生成的：

  • 它將 Base64Url 編碼後的標頭、Base64Url 編碼後的 payload，以及一個秘密金鑰 (secret)，一起使用簽名演算法（如 $HS256$）進行雜湊運算。
  • 只有伺服器知道這個秘密金鑰。當伺服器收到 JWT 時，它會使用相同的演算法和秘密金鑰重新計算簽名。如果計算出的簽名與 Token 中的簽名匹配，則證明 Token 是有效的，且未被篡改。

JWT 的運作流程（以授權為例）

  1. 使用者登入： 使用者透過帳號密碼登入。
  2. 伺服器發行 Token： 驗證成功後，伺服器建立一個 JWT，用秘密金鑰進行簽名。
  3. 返回 Token：將 JWT 發送給客戶端
  4. 客戶端儲存 Token： 客戶端（例如瀏覽器）將 JWT 儲存起來（通常是放在 localStorage 或 Cookie 中）。
  5. 後續請求： 客戶端在後續的每一個需要授權的請求中，將 JWT 放在 Authorization 標頭中（通常格式為 Bearer <token>）發送給伺服器。
  6. 伺服器驗證：
    • 伺服器檢查 JWT 的格式、過期時間 (exp) 等。
    • 伺服器使用秘密金鑰驗證簽名。
    • 如果驗證通過，伺服器信任 Token 裡的資訊（例如使用者 ID、權限），並處理請求。

JWT 的優缺點

優點：

  • 無狀態（Stateless）：伺服器不需儲存 Session 資訊
  • 跨域友好：可以在不同域名間，適用於微服務架構；相較之下，傳統 Cookie Session 容易遇到 CORS 問題。
  • 移動端友好：適合 App 使用
  • 傳遞輕巧，沒有額外儲存成本
  • 性能好：可存放一些使用者資訊，不需要查詢數據庫

缺點：

  • 無法主動撤銷：Token 發出後，在過期前都有效
  • 資訊不宜過多：Token 會隨著每次請求攜帶，Payload 不應包含敏感或過大的資料。
  • 密鑰洩露風險：如果密鑰被盜，所有 Token 都不安全
